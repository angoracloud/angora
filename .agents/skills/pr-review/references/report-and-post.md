# Report and posting

## Severity

| Severity | Means | Examples in this repo |
|---|---|---|
| **Blocker** | Must be fixed before merge | An already-applied migration edited in place; a route calling a repository; a copyleft or open-core dependency; a `^`/`~`/`LATEST` version; `minimumReleaseAge` weakened; a failed-login path revealing *why* it failed; a credential or `.env` in the diff; a required CI check red |
| **Major** | Should be fixed | New behavior with no assertion that would catch its removal; a hardcoded literal that belongs in a constants module; `.env.example` not synced with a new compose variable; the §Version Constraints table not updated; docs not updated for a behavior change; no linked issue |
| **Minor** | Worth fixing | Readability, naming, small duplication, a missing negative-path test on non-critical code |
| **Question** | Genuinely ambiguous — ask, do not assert | "Is `deleted_at` meant to be user-visible?" · "I couldn't determine the license for X — which did you check?" |
| **Info** | Context, no action expected | "No frontend test infrastructure exists (`README.md` §Limitations)" · "Branch name is lowercase; the ruleset accepts it and other branches do the same" |

`Question` exists so low-confidence observations have somewhere to go other than being asserted
as defects. Use it. It is a false-positive control, not a politeness device.

## Finding shape

Every finding carries all five fields. No exceptions.

```
[MAJOR] apps/frontend/src/hooks/useDiscordServers.ts:113 — Confirm text hardcoded in the hook
  What:   The delete confirmation string is typed inline instead of coming from
          CONFIRM_MESSAGES in src/constants.ts.
  Source: apps/frontend/AGENTS.md, "Constants discipline" bullet — message *templates* that
          take an argument (CONFIRM_MESSAGES, TOAST_MESSAGES) live in src/constants.ts.
  Fix:    Add CONFIRM_MESSAGES.DELETE_SERVER(name) to src/constants.ts and call it here.
  Confidence: Confirmed — read the full file; `grep -rn CONFIRM_MESSAGES src/` shows no such entry.
```

- A **conformance** finding without a `Source:` quote does not get reported.
- A **correctness** finding without a concrete inputs → wrong-output scenario does not get
  reported.
- `Confidence:` is `Confirmed` (you verified it) or `Plausible` (you could not fully verify —
  say what you could not check).

## Verdict

Deterministic mapping — do not freelance:

| Condition | Verdict |
|---|---|
| Any Blocker | **Request changes** |
| ≥3 Majors, or any Major touching auth, migrations, or dependencies | **Request changes** |
| 1–2 other Majors | **Approve with changes** |
| Only Minor / Question / Info | **Approve with nits** |
| Nothing | **Approve** |
| Requirements ambiguous in a way you cannot resolve | **Needs author input** |
| Draft PR, empty diff, or CI has not run | **Cannot review** (say which) |

Every report ends with:

> Advisory review by an agent. This is not a GitHub approval — `main` requires one human
> approval, and this skill deliberately never touches that control.

## Terminal layout

1. **Header** — `#52 · Implement soft delete for Discord servers · angora-51-… → main · 17 files, +367/-6 · CI 4/4 pass · Closes #51`
2. **Verdict** plus a 2–3 sentence summary of what the PR does and the shape of the findings.
3. **Findings**, grouped by severity, Blockers first.
4. **Requirements checklist** — a table of criterion → Met / Partially / Not met / Not statically
   verifiable, each with evidence.
5. **Coverage & limits** — what you did *not* verify, every time. For example: "No build or test
   was run locally; build, lint, typecheck, and test status is taken from `gh pr checks` (4/4
   green). Runtime behavior of the new endpoint was not exercised." A review that says what it
   did not check is trustworthy; one that implies it verified behavior is not.

## Posting flow

1. Read existing comments **first** and drop findings a human or a previous run already raised.
   Branch protection requires conversations resolved, so every duplicate comment is manual cleanup
   for someone. If a prior agent comment exists, offer a **delta** review ("new since `<sha>`")
   rather than reposting.
2. Print the **exact rendered comment body** — the thing that will land on GitHub, not a summary
   of it.
3. Ask one yes/no question: *"Post this as one comment on PR #52 as @<user>?"*
4. On an explicit yes only: write the body to the scratchpad (never the worktree) and
   `gh pr comment "$PR" --body-file "$SCRATCH/pr-review-$PR.md"`. Print the returned URL.
5. In the comment body, collapse each severity group in `<details>` when there are more than 8
   findings. Footer: `Generated by .agents/skills/pr-review`.

### Hard prohibitions

- **Never `gh pr review`** in any form — not `--approve`, not `--request-changes`, not
  `--comment`. `main` requires one human approval with stale-review dismissal; an agent that could
  approve would quietly hollow out that control.
- No inline/line-level review comments. One comment, or none.
- No editing the PR body, title, labels, assignees, or milestone.
- No closing, merging, or reopening.
- No resolving conversations.
- No `@`-mentions — they generate notifications for people who did not ask.
- Never more than one comment per run.

  by the TanStack Query `src/hooks/discordQueries.ts`. All three frontend findings above are
  therefore rebase artifacts and must collapse into **one** aggregated Major, not three-plus

Should **not** report (false-positive controls):

- The new Ktor artifacts carry the `-jvm` suffix and resolve to Apache-2.0 from the POM.
- `V7__add_deleted_at_to_discord_servers.sql` uses the next free number, adds no already-applied

  `assertTrue(repository.findAll().isEmpty())` after `softDelete`, plus the unknown-id null case

  flagging it as a coverage gap is a false positive.

hits, ≤1 invention, and zero findings from the second list.
